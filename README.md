## Trade-offs: Архитектурные решения проекта

### SPA or Framework with SSR

Выбор сделан в пользу SPA, так как чат не предполагает SSR/SSG, где критичны SEO.

- **Жертвуем:** SEO _(контент не индексируется поисковиками)_, временем первой загрузки _(initial bundle + data fetching)_
- **Получаем:** Более отзывчивый интерфейс после загрузки, отсутствие задержек на серверных перерендерах, более простой деплой _(только статика)_

### Vite or Webpack

Выбран Vite как сборщик для разработки и продакшен-билда.

- **Жертвуем:** Огромной экосистемой плагинов Webpack (но Vite уже догнал по основным сценариям), максимальной кастомизируемостью на грани извращений
- **Получаем:** Мгновенный запуск dev-сервера (даже на больших проектах), мгновенный HMR (горячая замена модулей), прозрачную конфигурацию (конфиг не спрятан в недрах — ты его видишь и контролируешь), отличную скорость сборки на продакшене, меньше боли с настройкой

### Default or FSD or ED

Выбран ED (Evolution Design) — архитектура, основанная на модулях и гибких слоях, без избыточной жёсткости FSD.

- **Жертвуем:** Огромным сообществом и готовыми примерами FSD, привычной структурой со слоями pages/widgets/entities, строгими ограничениями, которые дисциплинируют команду
- **Получаем:** Гибкость _(можно начинать с одного файла и усложнять модуль по мере роста)_, отсутствие оверхед-абстракций на старте, явное разделение на features (основная логика) и services _(переиспользуемые бизнес-модули)_, возможность хранить бизнес-логику в shared _(в отличие от FSD)_, поддержку подмодулей и групп, 4 готовые модификации _(от small до monorepo)_

### ESLint + Prettier or Biome

Выбрана связка ESLint + Prettier из-за зрелости.

- **Жертвуем:** Огромной экосистемой правил, проверенную годами стабильность, поддержку любых экспериментальных фич JS/TS, максимальную гибкость кастомизации
- **Получаем:** скорость работы, одну зависимость вместо двух + дополнительные зависимости правил, простоту конфигурации

### React Router or TanStack Router

Выбран React Router из-за большей зрелости и лучшей совместимости с React Compiler _(при билде компоненты разбиваются на мелкие JS-файлы — с TanStack Router такой оптимизации не сработало)_.

- **Жертвуем:** Встроенной типизацией поисковых параметров _(search params)_ на уровне TypeScript, более строгой типобезопасностью маршрутов, параллельными загрузчиками данных
- **Получаем:** Проверенный годами роутер с огромным сообществом, стабильную работу с React Compiler _(автоматическое code-splitting)_, отличную документацию, простую миграцию с легаси-кода

### Tailwind or CSS Modules or Styled Components

Выбран Tailwind CSS как утилитарный CSS-фреймворк.

- **Жертвуем:** Чистотой HTML _(много классов в разметке)_, разделением стилей и логики _(стили прямо в компонентах)_
- **Получаем:** Беспрецедентную скорость разработки _(не нужно придумывать имена классов)_, отсутствие переключения контекста _(не надо открывать отдельный CSS-файл)_, автоматическую очистку неиспользуемых стилей _(PurgeCSS)_, маленький итоговый CSS-бандл (!но иногда он может быть большой)

## Навигация по проекту

```
src/
├── app/         — страницы, слои и провайдеры
├── features/    — крупные куски функциональности проекта
├── services/    — код, который используется в нескольких фитчах
├── shared/      — утилиты, глобальный UI-kit, темы, конфиги
```

### Что можно, а что не стоит делать

|                | 🟢 Можно                                                     | 🔴 Лучше не стоит                                               |
| -------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| `app`          | добавлять провайдеры, лейауты и страницы                     | создавть компоненты                                             |
| `features/*`   | добавлять фичи                                               | делать перекрессные ссылки                                      |
| `services/*`   | виджеты и фитчи, которые используются в нескольких фитчах    |                                                                 |
| `shared/lib`   | логику глобальной инфраструктуры и хелперы                   | добалять компоненты и данные                                    |
| `shared/model` | добавлять общие типы, конфиги, данные и логику работы с ними | добалять компоненты, логику глобальной инфраструктуры и хелперы |
| `shared/ui`    | добавлять ui-kit компоненты                                  | добавлять что-то помимо компонентов                             |

### О чём помнить при разработке

- Один файл — один именованный экспорт компонента (исключая составные компоненты)
- Aliases обязательны для всех файлов с расширением .tsx, никакого `../../../../`
- index.ts — только для реэкспорта
- Все хуки именуются как `useSomething`
- Все стили — через app/index.css, Tailwind
- Строгий ESLint. Все автофиксы можно прогнать через `npm run lint`
- SVG иконки кладём в папку `shared/assets/...`
- Используй clsx для динамических вариантов
- Не забывать про public api

## Формат коммитов

Формат:

```text
type(feature): description
```

- _type_ - представляет собой символ
  - "+" - новая задача
  - "=" - правка
  - "~" - минорное изменение, на которое можно не обращать внимания
- _feature_ - название функциональности, в которой было произведлено изменение, по сути, жто имя папки в фитчах или shared
- _description_ - описане решенной проблемы

Примеры:

- `+ auth: добавлена страница логина`
- `= auth: ошибки валидации не отображались`
- `~ kit: добавлены компоненты конпки и поля`
