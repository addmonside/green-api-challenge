# Чат для MAX на GREEN-API HTTP API

Веб-интерфейс для отправки и получения текстовых сообщений в мессенджере MAX через
[GREEN-API](https://green-api.com/max). Отправка — методом
[SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/),
получение — long-poll через
[HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/)
(`ReceiveNotification` + `DeleteNotification`).

Интерфейс повторяет чат [web.max.ru](https://web.max.ru/): список чатов и переписка
с пузырями сообщений.

---

## Возможности

- вход по `idInstance` / `apiTokenInstance` с проверкой через `GetAccountSettings`
- создание чата по номеру телефона через `CheckAccount` (Россия `7…`, Беларусь `375…`)
- отправка текстовых сообщений, история последних 100 сообщений чата
- приём входящих текстовых сообщений в реальном времени
- разделители и метки времени, состояние «контакт был(а) только что / минуты назад»

Клиент и валидаторы к GREEN-API генерируются из Postman-коллекции
(`pnpm gen:api`), хенд-written схемы лежат в `scripts/postman-to-openapi.mjs`.

---

## Требования

- [Node.js](https://nodejs.org/) 20+
- [pnpm](https://pnpm.io/)
- аккаунт GREEN-API с инстансом, авторизованным в MAX
- macOS / Linux: утилита `mkcert` (ставится автоматически плагином, при первом запуске
  попросит пароль администратора)

## Быстрый старт

```bash
pnpm install
cp .env.example .env
```

Заполните `.env` — как минимум `VITE_API_URL` (базовый URL вашего GREEN-API).

Дальше — **включите приём уведомлений на инстансе** (см. следующий раздел, без этого
входящие сообщения приходить не будут) — и запустите проект:

```bash
pnpm dev
```

Откройте [https://localhost:3000](https://localhost:3000) и войдите, указав
`idInstance` и `apiTokenInstance` из личного кабинета GREEN-API.

Проект работает по HTTPS локально: GREEN-API не принимает запросы с небезопасного
-origin, а `mkcert` выпускает для `localhost` доверенный сертификат. При первом
запуске dev-сервера macOS попросит пароль администратора для установки корневого
сертификата — это нужно только один раз.

## Настройка инстанса: обязательный шаг

Технология HTTP API работает через очередь уведомлений, а не через вебхуки. Чтобы
`ReceiveNotification` начал отдавать сообщения, инстанс должен быть переключён в
режим HTTP API. Это делается в личном кабинете (раздел «Настройки» → «Webhook»)
или методом `SetSettings`:

```bash
curl -X POST \
  "https://api.green-api.com/waInstance{{ID_INSTANCE}}/setSettings/{{API_TOKEN_INSTANCE}}" \
  -H "Content-Type: application/json" \
  -d '{
    "webhookUrl": "",
    "incomingWebhook": "yes",
    "outgoingWebhook": "yes",
    "stateWebhook": "yes"
  }'
```

- `webhookUrl: ""` — очищает адрес вебхука, иначе уведомления уходят туда, а не в очередь
- `incomingWebhook` / `outgoingWebhook` / `stateWebhook: "yes"` — включают нужные типы событий

> **Если пропустить этот шаг, отправка сообщений будет работать, а получение — нет:**
> очередь уведомлений останется пустой. Проверить можно так — сообщение должно
> появиться в чате в течение `VITE_RECEIVE_TIMEOUT` секунд после ответа собеседника
> в MAX.

Уведомления, которые не забрали через `ReceiveNotification`/`DeleteNotification`,
хранятся в очереди 24 часа — в пределах этого окна чат подхватит их при повторном
открытии.

## Как пользоваться

1. Перейдите на сайт и введите `idInstance` и `apiTokenInstance`.
2. Укажите номер телефона получателя и нажмите «Создать чат» — приложение проверит
   номер через `CheckAccount` и откроет переписку.
3. Напишите текст и отправьте — сообщение уйдёт в MAX через `SendMessage`.
4. Ответьте в MAX с другого устройства — сообщение появится в чате автоматически.

Номер вводится без `+` и пробелов: `79991234567` или `375291234567`.

## Переменные окружения

Файл `.env` в корне (шаблон — `.env.example`), все переменные с префиксом `VITE_`
попадают в клиентский бандл.

| Переменная              | По умолчанию | Назначение                                                                 |
| ----------------------- | ------------ | --------------------------------------------------------------------------- |
| `VITE_API_URL`          | —            | Базовый URL GREEN-API без `/v3`. Обязателен: без него приложение не стартует |
| `VITE_RECEIVE_TIMEOUT`  | —            | Таймаут long-poll в секундах, GREEN-API принимает от 5 до 60                  |
| `VITE_DEVTOOLS_ENABLED` | `false`      | `true` — показывать панель TanStack Query Devtools                           |

`VITE_RECEIVE_TIMEOUT` и `VITE_DEVTOOLS_ENABLED` задаются в `.env.example` — скопируйте
файл и значения подхватятся.

Файл `.env` не коммитится — в репозитории лежит только `.env.example` без секретов.

## Навигация по проекту

```
src/
├── app/         — точка входа, провайдеры, роутер
├── features/    — крупные куски функциональности (auth, chat, messages, session, utility)
├── services/    — код, который используется в нескольких фичах (account, contacts)
├── shared/      — утилиты, модель, конфиги, UI-кит
│   ├── api/     — сгенерированный клиент GREEN-API, схемы, обработка ошибок
│   ├── lib/     — инфраструктура и хелперы
│   ├── model/   — типы, конфиги, данные
│   └── ui/      — компоненты (ui/kit — сгенерированные shadcn-компоненты)
```

### Что можно, а что не стоит делать

|                | 🟢 Можно                                                      | 🔴 Лучше не стоит                                             |
| -------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |
| `app`          | добавлять провайдеры, лейауты и страницы                      | создавать компоненты                                          |
| `features/*`   | добавлять фичи                                                | делать перекрёстные ссылки                                   |
| `services/*`   | виджеты и фичи, которые используются в нескольких фичах       |                                                               |
| `shared/lib`   | логику глобальной инфраструктуры и хелперы                    | добавлять компоненты и данные                                 |
| `shared/model` | общие типы, конфиги, данные и логику работы с ними           | добавлять компоненты, инфраструктуру и хелперы                |
| `shared/ui`    | добавлять UI-кит компоненты                                   | добавлять что-то помимо компонентов                           |

### О чём помнить при разработке

- Один файл — один именованный экспорт компонента (исключая составные компоненты)
- Для `.tsx` обязателен алиас `@` → `src/`, никаких `../../../../`
- `index.ts` — только для реэкспорта, за исключением `shared/ui/kit`
- Все хуки именуются как `useSomething`
- Все стили — через Tailwind, глобальные стили в `src/app/app.css`
- Строгий Biome: автофиксы — `pnpm lint:fix`, форматирование — `pnpm format`
- SVG-иконки кладём в `**/assets/icons/` — `vite-plugin-svg-sprite` превращает их в React-компоненты
- Схемы GREEN-API правятся в `scripts/postman-to-openapi.mjs`, потом `pnpm gen:api`.
  Файлы в `src/shared/api/generated/` руками не редактируются — их перезапишет кодогенерация
- Не забывайте про public API модуля

## Формат коммитов

```text
type(feature): description
```

- _type_ — символ:
  - `+` — новая задача
  - `=` — правка
  - `~` — минорное изменение, на которое можно не обращать внимания
- _feature_ — название функциональности, в которой произведено изменение (по сути, имя папки)
- _description_ — описание решённой проблемы

Примеры:

- `+ auth: добавлена страница логина`
- `= chat: ошибки валидации не отображались`
- `~ kit: добавлены компоненты кнопки и поля`

## Trade-offs: архитектурные решения проекта

### SPA or Framework with SSR

Выбор сделан в пользу SPA, так как чат не предполагает SSR/SSG, где критичен SEO.

- **Жертвуем:** SEO _(контент не индексируется поисковиками)_, временем первой загрузки _(initial bundle + data fetching)_
- **Получаем:** более отзывчивый интерфейс после загрузки, отсутствие задержек на серверных рендерах, более простой деплой _(только статика)_

### Vite or Webpack

Выбран Vite как сборщик для разработки и продакшен-билда.

- **Жертвуем:** огромной экосистемой плагинов Webpack (но Vite уже догнал по основным сценариям), максимальной кастомизируемостью на грани извращений
- **Получаем:** мгновенный запуск dev-сервера (даже на больших проектах), мгновенный HMR (горячая замена модулей), прозрачную конфигурацию (конфиг не спрятан в недрах — ты его видишь и контролируешь), отличную скорость сборки на продакшене, меньше боли с настройкой

### Default or FSD or ED

Выбран ED (Evolution Design) — архитектура, основанная на модулях и гибких слоях, без избыточной жёсткости FSD.

- **Жертвуем:** огромным сообществом и готовыми примерами FSD, привычной структурой со слоями pages/widgets/entities, строгими ограничениями, которые дисциплинируют команду
- **Получаем:** гибкость _(можно начинать с одного файла и усложнять модуль по мере роста)_, отсутствие оверхед-абстракций на старте, явное разделение на features (основная логика) и services (переиспользуемые бизнес-модули)_, возможность хранить бизнес-логику в shared _(в отличие от FSD)_, поддержку подмодулей и групп, 4 готовые модификации _(от small до monorepo)_

### ESLint + Prettier or Biome

Выбран Biome (lint + формат + тайпчек в dev-сервере через `vite-plugin-checker`).

- **Жертвуем:** огромной экосистемой правил ESLint, проверенной годами стабильностью, поддержкой любых экспериментальных фич JS/TS, максимальной гибкостью кастомизации
- **Получаем:** скорость работы, одну зависимость вместо ESLint + Prettier, единый конфиг, проверку TS и линта прямо в dev-оверлее

### React Router or TanStack Router

Выбран React Router из-за большей зрелости и лучшей совместимости с React Compiler _(при билде компоненты разбиваются на мелкие JS-файлы — с TanStack Router такой оптимизации не сработало)_.

- **Жертвуем:** встроенной типизацией поисковых параметров _(search params)_ на уровне TypeScript, более строгой типобезопасностью маршрутов, параллельными загрузчиками данных
- **Получаем:** проверенный годами роутер с огромным сообществом, стабильную работу с React Compiler _(автоматическое code-splitting)_, отличную документацию, простую миграцию с легаси-кода

### Tailwind or CSS Modules or Styled Components

Выбран Tailwind CSS как утилитарный CSS-фреймворк.

- **Жертвуем:** чистотой HTML _(много классов в разметке)_, разделением стилей и логики _(стили прямо в компонентах)_
- **Получаем:** беспрецедентную скорость разработки _(не нужно придумывать имена классов)_, отсутствие переключения контекста _(не надо открывать отдельный CSS-файл)_, автоматическую очистку неиспользуемых стилей _, маленький итоговый CSS-бандл !_(но иногда он может быть большой)_

### Сгенерированный клиент или ручной

Клиент GREEN-API и zod-схемы генерируются из Postman-коллекции: руками пришлось бы
поддерживать восемь эндпоинтов, два из которых (`ReceiveNotification`,
`DeleteNotification`) вручную вызываются из поллера.

- **Жертвуем:** контролем над сгенерированным кодом _(правки в `src/shared/api/generated/` перезаписываются)_, возможностью описать контракт шире, чем он есть в коллекции
- **Получаем:** синхронизацию с документацией, единый `baseURL` и `path` во всех вызовах, валидацию ответов на границе сети, типизацию из коробки
